# Create a Sublime Package

Build packages that fit this repository's layout and release pipeline. Keep the
implementation portable, testable outside Sublime where practical, and safe to
hot-upgrade through Package Control.

## Inspect first

1. Read the repository status and preserve unrelated changes.
2. Inspect `repository.json`, `scripts/build_packages.py`,
   `.github/workflows/release.yml`, and the closest existing package.
3. Confirm the package name, commands, settings, supported syntaxes, and whether
   it must be installed unpacked.
4. Treat Python 3.8 as the Sublime plugin runtime unless the repository changes
   its declared version.

## Create the package

Place the package at `packages/<PackageName>/`. Include only files the package
actually needs. A typical package contains:

```text
packages/<PackageName>/
├── .python-version
├── <PackageName>.py
├── <PackageName>.sublime-settings
├── Default.sublime-commands
├── Main.sublime-menu
├── README.md
├── LICENSE
├── package_helpers/
└── tests/
```

- Keep the Sublime-facing entrypoint thin. Put parsing, resolution, API, and
  transformation logic in ordinary Python modules that unit tests can import.
- Use async Sublime events and worker threads for filesystem, network, and
  subprocess work. Marshal UI updates back through `sublime.set_timeout`.
- Escape any value inserted into minihtml and validate remote responses before
  caching or rendering them.
- Add `.no-sublime-package` only when runtime files must be directly accessible
  on disk, such as executables loaded by path.
- If the entrypoint imports helper modules, explicitly reload those helpers
  before binding new symbols. Sublime may retain submodules across a Package
  Control hot-upgrade.

## Handle platform dependencies

- Do not add native executables, generated binaries, vendored runtimes, or
  platform-specific archives without explicit user approval.
- Prefer a small adapter per platform and discover external commands with
  `shutil.which` or an explicit package setting.
- Keep fallback order deterministic and return an actionable error when no
  adapter is available.
- When a binary is explicitly approved, record its source, version, license,
  checksum, supported architectures, and executable-bit verification.

## Register the package

Update every registry that enumerates packages:

1. Add the package name to `PACKAGES` in `scripts/build_packages.py`.
2. Add a schema-compatible entry to `repository.json`. Release assets must be
   named `<PackageName>.sublime-package`.
3. Add the asset to `.github/workflows/release.yml`.
4. Add the package to the root `README.md` package list.

Package archives must contain package contents at the archive root, never an
extra `<PackageName>/` directory. Keep tests, caches, metadata generated by
Package Control, and development-only files out of release assets.

## Test and verify

Add focused unit tests for parsing and failure cases. Run the package tests with
its directory on `PYTHONPATH`, then verify the complete release build:

```bash
PYTHONPYCACHEPREFIX=/private/tmp/sublime-pycache \
  PYTHONPATH=packages/<PackageName> \
  python3 -m unittest discover -s packages/<PackageName>/tests -v

PYTHONPYCACHEPREFIX=/private/tmp/sublime-pycache \
  python3 -m py_compile packages/<PackageName>/<PackageName>.py

python3 scripts/build_packages.py --output /private/tmp/sublime-package-build
git diff --check
```

Inspect the generated archive when packaging rules change. For runtime behavior
that depends on Sublime APIs, install or reload the package only when the user
has asked for it, then verify the loaded package rather than only the source
tree.

## Commit and release

- Use Conventional Commits and keep implementation, tests, manifest, and build
  integration in a reviewable change.
- Do not push, tag, publish a release, or mutate the user's Sublime installation
  unless the user explicitly requests that action.
- Before a requested release, ensure the worktree is clean, all tests and archive
  verification pass, and the semantic-version tag points at the intended commit.
- After publishing, verify the GitHub release assets and the version actually
  installed by Package Control. A successful workflow alone is not sufficient.
